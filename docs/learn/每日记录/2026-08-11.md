## 今日概念

- `OverrideCallback()` 只能替换构造时已存在于 `functionMap` 的方法。
- 同步 `Connect()` 中，main 线程读取请求、执行请求回调并写普通响应。
- Writer 线程不执行 Tool，也不写普通工具响应；它只消费通知队列并写异步通知。
- 因此耗时 Tool 会阻塞同步请求循环，而不是被 Writer 线程后台执行。
- Plugin 通过函数指针回调发送通知，避免直接依赖 `Server` 类。
- Notification 先进入 FIFO 队列，由 Writer 消费，形成生产者—消费者解耦。
- `progressToken` 关联长任务的一系列进度通知；JSON-RPC `id` 关联请求与最终响应。
- `ConnectAsync()` 只把串行请求循环搬到 Reader 线程，不提供多请求并发。
- Reader 调用 `ReadAsync()` 后立即 `future.get()`，中间没有并行工作，异步收益有限。
- 源码缺陷：`ConnectAsync()` 没有像 `Connect()` 一样调用 `transport_->Start()`，返回 `true` 不能证明 Transport 已成功启动。
- `ITransport` 隔离 Server 与具体通信方式；Transport 负责消息边界，不负责 MCP 业务解析。
- `Read()` 的隐式契约是返回一条完整 JSON-RPC 消息；当前 `{0, ""}` 无法清楚区分 EOF、停止、错误和空消息。
- STDIO 使用两条匿名管道实现双向通信，以换行符分隔单行 JSON-RPC；Server stdout 必须只承载协议消息。
- Client 使用缓冲区处理半包和多包，但当前还存在非阻塞忙循环、单次 `write()` 和空行/EOF 混淆问题。
- SSE 本身承担 Server→Client 持续事件流；Client→Server 使用独立 HTTP POST。
- POST HTTP 200 只确认请求已入 incoming queue，真正 JSON-RPC Response 从既有 SSE 长连接返回。
- Session ID 用来关联独立的 POST 与 SSE 连接；当前实现没有按 Session 隔离队列和状态，因此不能可靠支持多 Client。
- SSE `: ping` 是传输层保活注释；`notifications/progress` 是需要 MCP Client 理解的应用层业务通知。
- HttpStream 当前只有接口骨架：未接入 main 启动选择，且构造、读写和 HTTP Handler 均未形成可运行闭环。
- PluginAPI 使用 C 链接导出固定入口，并通过包含函数指针的结构体向 Server 暴露插件能力。
- `extern "C"` 固定导出符号的链接名称，`PLUGIN_API` 控制符号可见性，`PluginAPI` 结构体才是 Host 获得的函数表。
- 一个 Plugin 当前只能声明一种 `PluginType`，但该类型下可以包含多个 Tool、Prompt 或 Resource。
- Plugin 元数据和请求/响应指针必须遵守生命周期与所有权约定；跨模块分配和释放应由同一模块配对。
- Loader 的正确生命周期为 `dlopen → dlsym → Create → Initialize → 使用 → Shutdown → Destroy → dlclose`，中途失败需按已获得资源逆序回滚。
- 动态库应按稳定顺序加载，以保证行为和测试可重复；存在依赖时按依赖顺序加载、逆序卸载。

## 自测题

- `writer_running_` 改变后需要 `queue_cv_.notify_one()`，否则处于 `wait()` 的 Writer 线程无法及时重新检查退出条件。
- `Read()` 可能阻塞，单独修改 `isStopping_` 不会让控制流返回循环条件处。
- `joinable()` 只表示线程对象仍关联尚未 `join()`/`detach()` 的线程，不证明线程函数仍在运行。
- 析构函数调用 `Stop()` 是 RAII 兜底，防止调用者忘记释放 Transport 和线程。
- 纠正：同步 `tools/call` 的 Tool 执行发生在 main 线程；耗时 Tool 会阻塞后续普通请求。Writer 线程只写异步 Notification，不处理普通请求或响应。
- Notification 自测全部通过：Writer 不执行 `progress_test`；函数指针用于解耦 Plugin 与 Server；通知队列减少通知 I/O 对生产者的同步阻塞；耗时 Tool 期间不能处理新的普通请求；普通响应和通知分别由请求线程与 Writer 线程写出。
- `ConnectAsync()` 自测通过：Reader 线程执行 `HandleRequest()`；请求仍串行；立即 `future.get()` 限制异步收益；后台错误无法由先前的 `true` 表示；真正并发至少需要 Request Queue 和 Worker 线程。
- 补充纠正：当前 `ConnectAsync()` 未调用 `Transport::Start()`，其成功返回比“连接成功”更弱。
- SSE 重点检查：已掌握双向路径、incoming/outgoing 队列和 Session 用途。纠正：`{"status":"received"}` 确认 POST 已入队，不负责创建 SSE 连接，也不是 MCP 最终响应。
- PluginAPI 自测整体通过。纠正：`PLUGIN_API` 是导出属性而非函数表；类型限制作用于 Plugin；`DestroyPlugin()` 是 Host 必须调用、由 Plugin 决定具体释放行为的 ABI 契约。
- PluginsLoader 自测掌握加载失败清理和卸载顺序。补充：`dlclose()` 后函数地址可能失效；路径排序用于确定性；A 依赖 B 时加载 B→A、卸载 A→B。
